## Part 4: Missing API Endpoints (Concrete Gaps)

### Gap 1: Inventory List Endpoints

**Workflow Impact:** Workflows 1-2, 7-8

**Current State:**
- Backend stores: snapshots table with source='netbox' + source='live'
- Frontend cannot query: "Give me all devices from latest NetBox snapshot"

**Why Matters:**
- Dashboard needs to show "Expected Inventory" card
- Dashboard needs to show "Live Inventory" card
- Comparison view needs to show "What devices exist in NetBox"

**Workaround:** Query findings and reconstruct from differences (poor UX)

**Concrete Implementation:**
```python
@router.get("/inventory/netbox", response_model=InventoryListResponse)
async def list_netbox_inventory(db_session: Session) -> InventoryListResponse:
    """List all devices from latest NetBox snapshot."""
    snapshot = await SnapshotRepository(db_session).get_latest(source='netbox')
    if snapshot is None:
        raise HTTPException(status_code=404, detail="No NetBox snapshot found")
    return InventoryListResponse(
        devices=[SnapshotDevice.from_snapshot(snapshot)],
        source="netbox",
        snapshot_id=snapshot.id
    )

# Same for /inventory/live
```

**Why It Was Missed:** M29.5 focused on variance detection, not inventory browsing.

### Gap 2: Device Comparison Endpoint

**Workflow Impact:** Workflow 7

**Current State:**
- Backend compares devices correctly
- Frontend must: (1) find all findings for a device, (2) manually construct side-by-side view

**Why Matters:**
- "Open device and see side-by-side comparison" is core operator workflow
- Requires single API call, not multiple queries + manual merging

**Concrete Implementation:**
```python
@router.get("/devices/{device_id}/compare", response_model=DeviceComparisonResponse)
async def compare_device(
    device_id: str,
    run_id: UUID | None = None,  # Latest run if not specified
    db_session: Session = Depends(get_db_session)
) -> DeviceComparisonResponse:
    """Compare expected vs observed state for a single device."""
    findings = await FindingRepository(db_session).list(device_id=device_id)
    return DeviceComparisonResponse(
        device_id=device_id,
        expected_state={...},
        observed_state={...},
        findings=findings
    )
```

**Why It Was Missed:** Emphasis was on findings list, not device detail view.

### Gap 4: Timeline/Historical Variance Endpoint

**Workflow Impact:** Workflow 15

**Current State:**
- Repository has: HistoryRepository.timeline() method (unused)
- Frontend must: Query all discovery runs, then all findings for each run, manually merge

**Why Matters:**
- "Show variance over time" is a key compliance dashboard feature
- Operator wants to see: "Device A was compliant on run #1, drifted on run #3"
- Single API call is much faster than N queries + client-side merging

**Concrete Implementation:**
```python
@router.get("/history/timeline", response_model=TimelineResponse)
async def get_timeline(
    start_date: datetime | None = None,
    end_date: datetime | None = None,
    device_id: str | None = None,
    db_session: Session = Depends(get_db_session)
) -> TimelineResponse:
    """Get historical variance across multiple discovery runs."""
    # HistoryRepository.timeline() already exists!
    timeline = await HistoryRepository(db_session).timeline(start_date, end_date, device_id)
    return TimelineResponse(entries=timeline)
```

**Why It Was Missed:** Focus was on single-run comparison, not historical trending.

## Part 5: M30 Scope Recommendation

### Constraint (from product)
"M30 remains aligned with the original frontend roadmap: Compliance & Results UI, but must incorporate the primary Network Operations Platform use case: NetBox expected state vs real network observed state and variance/drift visualization."

### What This Means

**Original M30 = Compliance & Results UI**
- Show compliance status
- Display pass/fail findings
- Report compliance trends over time

**New M30 (M29.5-informed) = Compliance & Drift Visualization**
- Show what M29.5 discovered: expected state vs observed state
- Visualize variance types (MISSING, UNEXPECTED, MODIFIED)
- Trend variance over multiple discovery runs
- Root cause compliance failures in network drift

### Proposed M30 Feature List

**Core Features (MVP):**

1. ✅ **Dashboard: Variance Summary Card**
   - "X devices in NetBox, Y discovered live, Z differences"
   - Uses `GET /api/v1/findings` + `GET /api/v1/comparison/{run_id}`
   - No new API needed

2. ✅ **Dashboard: Variance Trend Chart**
   - "Variance over last 7 days"
   - Uses `GET /api/v1/history/discovery-runs` (poll findings for each)
   - No new API needed (workaround acceptable for M30 MVP)

3. ❌ **Inventory Browser: Expected Inventory**
   - List devices from NetBox
   - Uses `GET /api/v1/inventory/netbox` (NEW ENDPOINT - M30 Scope Add)

4. ❌ **Inventory Browser: Live Inventory**
   - List devices discovered
   - Uses `GET /api/v1/inventory/live` (NEW ENDPOINT - M30 Scope Add)

5. ❌ **Device Detail: Side-by-Side Comparison**
   - Click device → see expected vs observed for all attributes
   - Uses `GET /api/v1/devices/{device_id}/compare` (NEW ENDPOINT - M30 Scope Add)

6. ❌ **Device Detail: Interface/VLAN Drill-Down**
   - Click interface → see details + variances
   - Uses `GET /api/v1/snapshots/{snapshot_id}/...` (NEW ENDPOINT - M30 Scope Add)

7. ❌ **Finding Details: Evidence Chain**
   - Click finding → see full trace back to snapshot records
   - Uses `GET /api/v1/findings/{id}` (mostly ready) + snapshot endpoints

8. ⚠️ **Compliance Results: Drift-Based Pass/Fail**
   - "Device compliant if no variances OR only expected variances"
   - Uses comparison results + policies (partially ready)
