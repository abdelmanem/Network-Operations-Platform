## BLOCKING DEFECTS

### DEFECT #1: Race Condition in Concurrency Protection

**Location:** [backend/app/api/v1/integrations.py:420-435](backend/app/api/v1/integrations.py)

**Code:**
```python
# Check if a job is already queued or running
active_job = (
    db_session.query(NetBoxSyncJobRecord)
    .filter(NetBoxSyncJobRecord.status.in_(["queued", "running"]))
    .first()
)

if active_job is not None:
    raise NetBoxIntegrationError(...)

# Create new sync job UUID and persist in PostgreSQL
job_id = uuid4()
repo.create_sync_job(job_id)
db_session.commit()
```

**Issue:** Check-then-act without atomicity. Two concurrent requests can both see no active jobs, then both create jobs.

**Scenario:**
1. Request A: Query finds no active jobs
2. Request B: Query finds no active jobs
3. Request A: Create job A, commit
4. Request B: Create job B, commit
5. Result: TWO concurrent jobs in database (intended: zero)

**Test Coverage Gap:** [tests/api/test_integrations.py:237](tests/api/test_integrations.py#L237)
```python
def test_sync_endpoint_concurrency_protection(...):
    repo.create_sync_job(uuid4())  # PRE-CREATE JOB
    db_session.commit()
    response = client.post("/api/v1/integrations/netbox/sync", headers=headers)
    assert response.status_code == status.HTTP_409_CONFLICT
```

This test is sequential, not concurrent. It does NOT test two simultaneous requests.

**Fix Required:** Add `SELECT ... FOR UPDATE` locking or database-level unique constraint on status.

**Blocking?** YES — Defeats core concurrency protection guarantee.

### DEFECT #2: Missing Transaction Rollback on Exception

**Location:** [backend/app/api/v1/integrations.py:110-140](backend/app/api/v1/integrations.py#L110-L140)

**Code:**
```python
try:
    snapshot = await inventory_service.synchronize(force_refresh=True)
    repo.add_netbox_snapshot(snapshot)  # Adds to session, NOT committed
    
    job.status = "succeeded"
    job.finished_at = datetime.now(UTC)
    db_session.commit()  # Commits both job AND snapshot
    
except Exception as exc:
    job.status = "failed"
    job.finished_at = datetime.now(UTC)
    job.error_message = str(exc)
    db_session.commit()  # No rollback() call!
```

**Issue:** If `add_netbox_snapshot()` raises an exception AFTER calling `session.add()`, the pending snapshot records remain in the session. The except block then commits the failed job AND the snapshot.

**Scenario:**
1. `inventory_service.synchronize()` succeeds
2. `repo.add_netbox_snapshot(snapshot)` begins:
   - Creates SnapshotRecord
   - Creates SnapshotDeviceRecord children
   - Calls `session.add(snapshot_record)`
3. Exception raised during child record creation or add()
4. Except block: modifies job, calls `db_session.commit()`
5. Result: Job marked failed AND snapshot partially persisted (inconsistent state)

**Fix Required:** Add explicit `db_session.rollback()` in except block before updating job.

**Blocking?** MEDIUM — Could cause partial snapshots in rare edge cases. Mitigated somewhat by immutability enforcement (snapshot records won't be updated), but violates atomicity guarantee.

## NON-BLOCKING RISKS

### RISK #1: Snapshot Immutability via ORM Listeners Only

**Protection:** Event listeners on before_update/before_delete → RuntimeError

**Exposure:** Raw SQL UPDATE/DELETE bypasses listeners (application uses SQLAlchemy, not raw SQL)

**Likelihood:** LOW (codebase enforces ORM usage)

**Recommendation:** Add database-level NOT NULL constraints and immutable triggers for defense-in-depth.

---

### RISK #2: Frontend Status Polling Not Implemented

**Impact:** Users must manually refresh to see sync status. Long-running syncs appear frozen.

**UX Risk:** HIGH (perception of unreliability)

**Correctness Risk:** NONE (endpoint works correctly, just not auto-polled)

**Recommendation:** Implement polling interval (setInterval every 5-10s) in SettingsPage.tsx

---

### RISK #3: No Explicit Transaction Isolation Configuration

**Current:** SQLAlchemy uses database default (PostgreSQL READ COMMITTED)

**Vulnerability:** READ COMMITTED allows phantom reads (exactly the concurrency race condition above)

**Recommendation:** Specify `isolation_level="SERIALIZABLE"` or use explicit SELECT FOR UPDATE

---

### RISK #4: Frontend Status Not Auto-Updating

**Backend:** Supports polling via GET /status

**Frontend:** No setInterval; manual refresh only

**Test Coverage:** Mock tests pass; E2E tests missing

**User Flow:** Click sync → Wait 30s → Manually click refresh → See result

**Recommendation:** Add Cypress/Playwright E2E test
