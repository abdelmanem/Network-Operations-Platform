# M30.3 — Real Network Integration & End-to-End Variance Validation Audit

## Executive summary

This audit is based on inspection of the actual runtime configuration and live endpoint behavior in the current workspace. It does not rely on mocks or fabricated data.

The current state is not ready for real network variance validation:

- The application is correctly loading the configured NetBox URL from the existing `.env` file.
- The live NetBox HTTPS endpoint is reachable, but the TLS certificate is self-signed and fails the default certificate validation built into the application client.
- The configured NetBox credentials are not validated successfully against the live server.
- No real Cisco discovery targets or transport credentials are configured in the repository or environment.
- The collector runtime is real and correctly wired to the real `CollectorRegistry`, but it has no valid runtime discovery inputs to execute against the real network.
- Therefore, no real NetBox expected-state inventory, no real live Cisco snapshot, and no real end-to-end comparison or variance findings could be produced from this environment as-is.

Recommendation: NOT READY.

## 2. Real NetBox runtime evidence

### 2.1 Current NetBox configuration

From the active `.env` file:

```env
NETBOX_URL=https://192.168.137.5
NETBOX_EXPECTED_VERSION=4.6.7
NETBOX_TIMEOUT_SECONDS=10
NETBOX_PAGE_SIZE=100
NETBOX_RETRY_MAX_ATTEMPTS=4
```

The app settings loader reads these values through `Settings` in `backend/app/config/settings.py`:

- `netbox_base_url: str = Field(default="", validation_alias="NETBOX_URL")`
- `netbox_token: str = Field(default="", validation_alias="NETBOX_TOKEN")`
- `netbox_expected_version: str = "4.6.7"`

The runtime proof is:

```text
SETTINGS_URL=https://192.168.137.5
TOKEN_SET=True
EXPECTED_VERSION=4.6.7
CLIENT_BASE_URL=https://192.168.137.5/
```

This confirms the application loads the configured NetBox URL and the token is populated in the active runtime configuration. The actual token value is not exposed in terminal output or logs here.

### 2.2 NetBox connectivity result

The application’s actual client path is:

- `backend/app/config/settings.py`
- `backend/app/integrations/netbox/client.py`
- `backend/app/integrations/netbox/service.py`

The runtime probe used the real application client with the configured settings and returned:

```text
HEALTH_ERROR=NetBoxTransportError:[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: self-signed certificate (_ssl.c:1028)
```

Interpretation:

- The client reached the server at `https://192.168.137.5`.
- The TLS handshake completed far enough to present a certificate.
- The failure is at certificate trust validation, not at DNS resolution or a complete network outage.
- The certificate is self-signed, which is a real TLS trust mismatch with the default HTTPX verification model.

This means the application cannot currently establish a trusted HTTPS connection to the active NetBox server under default secure settings.

### 2.3 NetBox authentication result

The live API was probed again with certificate verification disabled for inspection-only diagnostics. The result was:

```text
STATUS_HTTP=403
DEVICES_HTTP=403
```

This is not proof of successful login. It is proof that the configured credentials did not successfully authenticate to the live endpoint under the current environment state.

Important safety note: the token value was never printed in logs or output.

Conclusion:

- TLS trust is failing in normal secure mode.
- Authentication is not successful under the current real environment state.

### 2.4 NetBox version result

The application expects NetBox version `4.6.7` via `NETBOX_EXPECTED_VERSION`.

However, because the health check fails before the version can be validated, the actual detected version could not be confirmed from the running application. The version remains unresolved due to the combined TLS + authentication blockers.

Observed runtime state:

```text
EXPECTED_VERSION=4.6.7
```

Actual detected version: not available / not validated because the live health call fails before version validation occurs.

- `InventoryService.synchronize()` is therefore not proven to work against the real NetBox instance in the current environment.

## 3. Real Cisco discovery evidence

### 3.1 Which Cisco devices are currently configured for discovery

There are no static Cisco device entries configured in the repository or environment for discovery.

Evidence:

- No real device address list exists in `.env`.
- `backend/app/api/v1/jobs.py` builds discovery jobs from the request payload, not from stored config.
- `frontend/src/pages/DiscoveryPage.tsx` exposes a runtime form that accepts a target identifier and address.

The effective discovery configuration is dynamic and user-supplied at runtime; there is no preconfigured set of Cisco devices in the current workspace.

### 3.2 Where device addresses are configured

The real runtime model uses `DiscoveryTarget` and `CollectorRuntimeContext`:

- `backend/app/discovery/context.py`
- `backend/app/api/v1/jobs.py`

The address comes from the submitted job payload:

```python
target = DiscoveryTarget(
    identifier=str(target_payload.get("identifier", "")),
    address=str(target_payload.get("address", "")),
)
```

There is no environment-based or static Cisco discovery address list.

### 3.3 Where SSH/SNMP credentials are configured

The transport layer supports credential resolution but no real resolver is configured in the runtime application setup.

Evidence:

- `backend/app/core/application.py` creates `TransportManager()` without attaching a `CredentialResolver`.
- `backend/app/transports/manager.py` has a `credential_resolver` field, but it remains unset.
- There are no `SSH_USER`, `SSH_PASSWORD`, `SNMP_COMMUNITY`, or equivalent real credential entries in the environment or project files.

This means the application has no configured device credentials for real network discovery.

### 3.4 Which collectors will execute

The real collector registry is built by:

- `backend/app/core/application.py`
- `backend/app/collectors/cisco/factory.py`

The runtime registry includes:

- `CiscoIOSInventoryCollector` for Catalyst families
- `CiscoCE500InventoryCollector`
- `CiscoAironetInventoryCollector`

The real collector registration sequence is in `register_all()`.

### 3.5 Which transport will be selected

The selection order is explicit in `backend/app/collectors/cisco/base.py`:

```python
TRANSPORT_PRIORITY = (SSH, SNMP, HTTP)
DEFAULT_TRANSPORT_NAMES = {
    SSH: ("netmiko", "paramiko"),
    SNMP: ("pysnmp",),
    HTTP: ("httpx",),
}
```

Therefore, the selector prefers:

1. SSH
2. SNMP
3. HTTP

This is the real transport selection logic, not fake/test logic.

### 3.6 Whether the collector runtime uses the real CollectorRegistry rather than fake/test collectors

Yes. The real runtime path is:

```python
collector_registry = build_cisco_inventory_registry(transport_manager)
collector_executor = CollectorExecutor(
    collector_registry=collector_registry,
    transport_manager=transport_manager,
    ...
)
```

This is in `backend/app/core/application.py`.

The runtime does not use a fake collector registry during the real application boot path.

### 3.7 Whether discovery can execute read-only commands against the real network

The code is designed to run read-only operations:

- SSH commands are drawn from inventory/system/interface/VLAN/power/POE/neighbor categories.
- SNMP uses `get_cmd` / `next_cmd` reads only.
- HTTP path is also read-only in the transport layer.

This is consistent with the intended safety model.

However, the real network has not been configured with actual discovery targets or credentials, so no real read-only discovery execution was performed. This environment is therefore not ready to run real network discovery.

### 3.8 Where the resulting live snapshot is persisted

The live snapshot is persisted through the application’s persistence layer:

- `backend/app/orchestration/workflow.py` calls `unit_of_work.snapshots.add_live_snapshot(...)`
- `backend/app/persistence/repositories.py` persists a `SnapshotRecord` with `source=LIVE`
- The database schema is defined in the Alembic migrations and the SQLAlchemy model layer

Thus, the live snapshot is persisted in the configured application database rather than in a mock store or a local file.

## 7. Security and read-only verification

### Security posture

- The application uses HTTPS when the configured URL is trusted.
- The current NetBox endpoint is using a self-signed certificate, which is a real trust issue.
- The app does not disable TLS verification by default, which is the correct secure behavior.
- There is no code change to weaken TLS or bypass certificate validation in this audit phase.

### Read-only constraint

The collector implementation is designed to be read-only:

- SSH commands are collected for inventory/system/interface/VLAN reads.
- SNMP uses get/walk semantics only.
- No write back to NetBox is performed in the sync path.
- No discovery or mutation is performed on the Cisco devices in this inspection-only validation.

### Current blocker summary

The system is not allowed to move to real variance evaluation until the following are satisfied:

1. Trust the NetBox server certificate correctly (CA trust or explicit trusted root/cert configuration).
2. Confirm the NetBox token is valid for the live server.
3. Confirm the actual NetBox version is 4.6.7 or update the expected-version contract if a different real version is detected.
4. Configure at least one real discovery target with address and credentials.
5. Configure the credential resolver or equivalent secret setup for SSH/SNMP access.
6. Verify the real discovery environment is reachable from the application process and that the collector runtime executes read-only commands successfully.
